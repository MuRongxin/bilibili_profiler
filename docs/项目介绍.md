# B站弹幕发送者用户画像分析系统

> 输入一个 BV 号，回答一个问题：**这些弹幕都是谁发的，他们是什么人。**

纯 Python 3 实现的端到端分析流水线，约 1.16 万行代码、28 个模块，数据全部落本地 SQLite，不依赖任何外部服务。从采集、身份破解、行为检测、用户画像到交互式报告一条龙自动完成，全程断点可续、结果可缓存、风控可扛。

---

## 一、这个项目解决什么问题

B站弹幕是匿名的——弹幕接口只返回一个 CRC32 哈希（`mid_hash`），不返回发送者 UID。当一个视频的弹幕区/评论区爆发争执、水军刷屏、引战团建时，运营者和普通用户面对几千条匿名弹幕，无法回答：

- 刷得最凶的是同一个人还是一群人？是自发玩梗还是有组织行动？
- 这些"路人"是真的路人，还是某家粉丝的小号、换皮马甲？
- 谁在挑事，谁被围攻，争执因哪句话而起？
- 历次视频之间，哪些面孔反复出现？

本项目把这条链路完整跑通：**匿名弹幕 → 破解发送者身份 → 行为检测 → 逐个深度画像 → 可交互的分析报告**。

## 二、端到端流水线

输入 BV 号，一条命令（`python run.py <BV号>`）自动完成六个阶段，每个阶段独立断点续采、独立缓存：

| 阶段 | 做什么 | 关键机制 |
|---|---|---|
| 1. 弹幕采集 | 实时弹幕池 + 逐日历史弹幕快照合并 | 逐日落库、dmid 幂等去重、失败日记账补采 |
| 2. 评论采集 | 评论区全量（主评+楼中楼）+ 充电名单 + 互动弹幕 + 视频元信息 | 逐页游标检查点、IP 属地、UID 收割建库 |
| 3. 身份破解 | 把匿名 `mid_hash` 还原成真实 UID | CRC32 中间相遇反查 + 明文交叉验证（核心技术，见第三节） |
| 4. 行为检测 | 本地规则刷屏检测 + LLM 八类问题判定（弹幕与评论） | 组合计分、批次缓存、多厂商容错 |
| 5. 用户画像 | 对筛选出的重点用户四维度采集 + 规则画像 + LLM 深掘 | 阈值制动态定员、账号×IP 组合池并发采集 |
| 6. 报告生成 | 本地 Flask Web 交互式报告，八个标签页 | 整页缓存、数据指纹比对、打印样式导出 |

分析完毕自动启动报告服务并打开浏览器（可关）；`--batch` 支持批量分析多个视频；已分析过的视频重跑时自动只补新增弹幕与评论。

### 动态定员

不是所有发送者都值得深挖。系统按**兴趣分阈值制**动态决定画像名单：刷屏中/高风险、或问题弹幕命中的用户直接入选；名单规模随视频发送者总数浮动（保底 300 人、按 5% 上浮、绝对封顶 1000 人），可用 `--max-users` 手动覆盖。在此基础上，兴趣分 Top 20 再由 LLM 单人单调用深度挖掘。

## 三、核心技术：匿名发送者身份破解

弹幕接口只给 `mid_hash = CRC32(UID)`。CRC32 不可逆，但 UID 的取值空间有限，项目用三条路径交叉还原：

### 3.1 明文交叉验证（高置信度）

B站很多地方是明文 UID：评论区、充电名单、互动弹幕、视频元信息（UP主、联合投稿 staff、简介 desc_v2 的 @ 提及）。把这些明文 UID 正向算一遍 CRC32 建映射表，弹幕哈希直接查表命中。

其中"评论 UID 收割"是个持续投入的机制：专门翻评论区只为收集 UID 建映射库（不落评论内容，累计上限 500 页、断点续翻），像滚雪球一样持续提高后续视频的命中率。

### 3.2 MITM 中间相遇反查（数学破解）

对不在任何明文源里的哈希，用"中间相遇"（meet-in-the-middle）法暴力反解：预计算 10 万条 UID 前缀表 + 5 位后缀表，把 O(10¹⁰) 的全空间穷举降为 O(10⁵) 的查表组合，单哈希约 49ms，覆盖全部 ≤10 位 UID。表惰性构建、双检锁保证线程安全。反查出多个候选时，经批量用户名片接口消歧。

### 3.3 全局映射库与置信度体系

- **全局映射库**（`global_uid_map` 表）跨视频沉淀可靠映射，解析率随使用次数累积提升。只有评论/充电/互动/元信息等**明文来源**才允许沉淀；纯 CRC32 破解结果不沉淀，防止潜在的碰撞误归因跨视频放大。冲突覆盖按"明文 > 破解"的来源优先级。
- **置信度分级**：每个解析结果带高/中/低置信度与碰撞风险标记。低置信度用户不进入画像（防张冠李戴），但在报告的"低置信度"页集中展示（UID、解析方式、mid_hash、弹幕内容样本），可人工复核后手动强制画像。

## 四、行为检测

### 4.1 刷屏检测（纯本地、可解释、只标记不删除）

四规则组合计分（取最高分、每多触发一条加成）：

1. **内容重复率**——同一人重复内容的占比；
2. **时间规律性**——发送间隔过于机械；
3. **变种相似度**——换皮刷屏（内容微调但结构雷同）；
4. **滑动窗口爆发**——短时间窗口内的发送频次 burst，而非只看全局平均。

在此之上还有两层补强：**全池 P95 相对离群**（跟同视频所有人比，而非绝对阈值，适配大小视频差异）和独创的**群体复读事件检测**——同内容 60 秒窗口内 ≥5 人 ≥8 条的接龙/+1 队列，专抓"一人一句"这种单人检测天然盲区的有组织玩梗/团建，并附全池分布自检行供阈值校准。

刷屏只标记风险等级（高/中/低），**绝不删除任何弹幕数据**。

### 4.2 LLM 问题内容判定（弹幕 + 评论，八类口径）

按二游社区语境调校的八类问题口径：**中二抒情 / 尬夸捧杀 / 引战阴阳 / 人身攻击 / 恶意剧透 / 广告引流 / 键政敏感 / 批评吐槽**。

- 弹幕 200 条/批、评论 100 条/批（总量上限 2000 条），并发 16 路，429 自动退避；
- **批次级缓存**：缓存 key = 视频 + 口径版本 + 模型 + 内容指纹，先解析校验成功才落缓存，坏响应进重试链，已完成批次重跑零 token 消耗；
- **多厂商容错**：deepseek（主用）/ 智谱 GLM / 小米 MiMo 三厂商，判定批次自动关闭或压低思考（推理 token 零成本、不占输出预算），失败自动换备用厂商，厂商内容审核拦截按批次跳过不中止整轮，整轮重试超 30 分钟熔断放弃并告警；
- 结果回写数据库，报告里按类别/严重度聚合到人。

### 4.3 问题评论作者直引

评论是明文 UID，无需破解。作者的问题评论达到阈值（严重度 ≥2 或命中 ≥2 条）时，凭明文 UID 直接进入画像名单（解析方式标"问题评论"），与弹幕破解名单汇合。

## 五、用户画像体系

### 四维度采集

对入选用户采集四个维度的数据（走账号×IP 组合池多号并行分片）：

1. **主页信息**——昵称、签名、等级、认证、院校等；
2. **互动足迹**——动态、投币点赞等公开行为；
3. **社交关系**——关注列表（被关注 UP 主的投稿词云在报告页悬停懒加载）、粉丝可见信息；
4. **行为模式**——在本视频及其他已分析视频中的弹幕/评论样本。

### 规则画像 + AI 深掘

- **规则画像**：本地规则引擎生成兴趣标签、活跃时段、行为特征等可解释结论；
- **AI 深掘**：兴趣分 Top 20 用户单人单调用 LLM，综合其弹幕原文、评论、四维数据生成叙事性画像，结果按用户缓存、跨视频复用。

### 跨视频串联

- 首页**跨视频重叠用户面板**：在 ≥2 个已分析视频都出现过的发送者，可展开看其在各视频的弹幕/评论明细；
- 用户卡片**"其他视频足迹"**区块：该用户在其他视频的言行样本；
- **用户互动时间线**页：单用户在全部已分析视频中的弹幕与评论按最近互动倒序排列。

## 六、Web 交互式报告

本地 Flask 服务（127.0.0.1:8000，不对外网开放），八个标签页：

| 标签页 | 内容 |
|---|---|
| **概览** | 视频信息、统计图表、弹幕密度时间轴（分桶直方图，点柱跳转视频对应时段核验）、群体复读事件区块（附全池分布自检）、解析质量区块（方式/置信度分布+碰撞风险人数）、操作条（重新生成/删除/导出/隐藏信息开关） |
| **用户画像** | 用户卡片：四维画像、AI 深掘、院校徽标、关注偏好 chips、其他视频足迹 |
| **弹幕浏览器** | 全量弹幕按时间/类型筛选，状态写入 URL 可分享；可勾选 mid_hash 手动触发强制分析（后台 job，失败明细透出可重试） |
| **问题弹幕榜** | 问题弹幕按类别/严重度聚合到人，附原文 |
| **争执焦点** | 见下文，本系统最具特色的页面 |
| **问题评论榜** | 全部问题评论按热度（点赞 + 回复数×权重）降序，楼中楼附父评原文 |
| **高回复评论** | 潜在争执热点：完整回复树按 parent_rpid 嵌套缩进、默认折叠可展开、楼主/UP主徽标、问题评论分色标注；悬停 600ms 弹该组讨论主题词云 |
| **低置信度** | 低置信度解析结果集中复核页，提示可经弹幕浏览器勾选强制画像 |

### 争执焦点还原

把问题回复按 `parent_rpid` 还原成 **"A 攻击 B"的边**，生成：

- **挑事者榜 / 被围攻者双榜**：挑事者成对展示"被攻击者原评 + 攻击原文"；被围攻者的受害原评按条去重只展示一次、各攻击者的攻击原文挂在其下；楼中楼向上多带一层上游还原对话链；名额随攻击边数动态浮动（保底 5、每 10 边 +1、封顶 20）；
- **顶部关系图**：多圆簇 SVG 布局——每个连通分量一个独立小圆簇（受害者居中、攻击者环绕），箭头线随攻击者分色、线粗映射攻击次数、节点大小映射攻击/被攻击次数；悬停节点高亮其全部关系边，点击定位到下方明细条目。

谁在拱火、谁被团建、因哪句话而起，一目了然。

### 报告的其他设计

- 整页 HTML 按 BV 号内存缓存，每请求比对六表聚合数据指纹（含头像缓存），后台 job 完成、误报标记、甚至外部进程直接改库都能自动检出重渲染；
- 标签页/筛选状态写入 URL，可直接分享定位；
- `@media print` 打印样式替代独立的"完整报告"页；
- Chart.js 与 wordcloud2 已本地化，纯离线环境可用。

## 七、工程化设计

### 7.1 对抗风控的全套设计

- **统一限速器**：所有请求走 `BiliAPIClient`，基础间隔 0.8–1.6s、高风险端点 2–4s（区间内随机取值消除固定节奏特征）；触发风控（-412 / HTTP 412 / 重签无效的 -352/-403）自适应倍率 ×1.5 上调（封顶 5.0），业务成功后缓慢回落；重试最多 3 次指数退避；WBI 端点自动重签，bili_ticket/buvid3 凭证失败负缓存后重试；
- **账号×IP 组合池**：多账号扫码登录（小号池自动发现），风控时自动"换号 + 切节点"重试，冷却按截止时刻锁外等待；多号并行分片采集，吞吐约等于账号数倍增；
- **内置代理核心**：零安装内嵌 mihomo，多机场订阅合并为 IP 池，跨地区跳跃轮换；死节点自动剔除进黑名单、TTL 复活，全灭时回退不过滤；核心二进制自动下载并**强制官方 SHA256 校验**；IP 池整体故障自动降级直连并定时重探恢复；
- **失败降级而非中断**：评论采集失败回退纯 CRC32 破解；LLM 失败只警告；单用户异常不拖垮整体流水线。

### 7.2 断点续采与增量更新

弹幕逐日、评论逐页、LLM 判定逐批、用户逐个落库并写检查点（`phase_state` 表）。Ctrl+C、崩溃、风控中断后重跑，一律从断点继续，不重复消耗 token 和请求配额。

已 done 的视频重跑转入增量模式：弹幕滚动补采最近 3 天、评论按时间序只翻新页（撞见已见整页即停，旧评论顺带刷新热度）、UID 收割断点续翻。

### 7.3 隐私与安全

- Web 服务只绑本机回环，非 GET 请求强制校验 Origin/Host 为本机（防 CSRF / DNS rebinding）；
- 全站**"隐藏信息"开关**：开启后昵称只留末字其余以颜文字代替、UID 除前三位打码，方便截图分享不泄露他人信息，页面缓存按开关分版本；
- Cookie 原子写入、权限 0o600；导出 CSV 防公式注入；SQLite WAL 模式保证多进程并发安全；
- 敏感配置（LLM Key、Cookie、数据库、订阅链接）全部在 `.gitignore` 排除，代理凭证文件在核心退出时自动删除。

### 7.4 人工纠偏闭环

问题弹幕（按内容）、问题评论（按 rpid）、刷屏判定（按发送者）都可一键标记"误报"：标记后展示层即时扣除、不计入聚合与疑似分，可撤销，跨重跑保留。判定系统 → 人工校验 → 数据沉淀的闭环。

## 八、技术栈与规模

- **语言**：纯 Python 3，无构建系统，扁平模块化（非包结构）；
- **依赖**（仅 11 项，全是常见库）：requests / lxml / openai / flask / qrcode / pillow / pycryptodome 等；
- **存储**：单文件 SQLite（WAL），全量弹幕、评论、画像、缓存、检查点都在本地；
- **前端**：无构建的原生 JS + 本地化 Chart.js / wordcloud2，数据经 JSON 内联注入；
- **规模**：28 个 Python 模块、约 1.16 万行代码（含 2600 余行的 Web 服务层）；
- **LLM**：OpenAI 兼容接口，deepseek / 智谱 GLM / 小米 MiMo 三厂商可切换，缓存按模型隔离支持 A/B 对比。

## 九、快速开始

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt

python login.py                 # B站 APP 扫码登录（Cookie 存本地复用）
python login.py alt1            # 额外登录小号 alt1（自动进入采集账号池）
python run.py BV1xxxxxxxxxx     # 分析视频，完毕自动打开报告
python run.py BV1xxxxxxxxxx --force        # 忽略缓存强制重跑
python run.py BV1xxxxxxxxxx --max-users 50 # 手动覆盖画像名额
python run.py --batch list.txt  # 批量分析（每行一个 BV 号，# 为注释）
python quick_test.py            # 冒烟测试（只分析刷屏 Top N，速度快）
python web.py                   # 单独启动报告服务（127.0.0.1:8000）
python web.py --stop            # 停止后台报告服务
```

需要有效登录态与真实网络环境；`config.py` 集中管理全部可调参数（限速、翻页上限、定员阈值、LLM 配置等），LLM Key 优先走环境变量。

## 十、使用边界说明

- 本项目面向**UP 主 / 运营者理解自己评论区生态、研究者观察社区行为模式**的场景，全部数据来自登录账号正常可访问的公开接口，分析结果仅存本地；
- 系统定位是"还原与呈现"而非"处置"：只标记、不删除、不举报、不自动发送任何内容；置信度体系的存在就是为了防止把身份安在错误的人头上；
- 内置隐私遮蔽开关供对外分享截图时保护他人信息；请遵守平台条款与当地法律，勿用于骚扰、人肉或其他侵害他人的用途。
