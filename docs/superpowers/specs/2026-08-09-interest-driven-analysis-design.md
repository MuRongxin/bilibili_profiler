# 兴趣驱动的弹幕发送者分析 — 设计文档

日期：2026-08-09
状态：已与用户对齐，待实现

## 背景与目标

用户提出 6 条改进：

1. 优先找出刷屏弹幕，从刷屏内容最多的开始分析；
2. 分析出弹幕"尬语"，并分析尬语的发送者；
3. 为实现前两条，先把全部弹幕获取到；
4. 发送弹幕的人若也发表了评论，展示他的评论内容；
5. 报告中用户的最近投稿应为超链接（新标签页直达）；
6. AI 画像分析重新设计。

## 关键约束（必须如实告知）

- **弹幕全集极限**：B站公开接口拿不到严格意义的全部历史弹幕。历史接口是按天的
  弹幕池快照，每日仅保留最新 1000 条，溢出的老弹幕被永久挤出。现有
  "实时池 + 逐日历史快照合并去重"已是公开接口的极限，本设计不改变采集方式。
- **限速是硬约束**：深度采集每人约 10-15 秒，动态定员必须有安全上限兜底。
- **降级而非中断**：尬语检测与 LLM 画像在未配置 `LLM_API_KEY` 或调用失败时跳过，
  不影响主流程。

## 已确认的设计决策

| 决策点 | 结论 |
|---|---|
| 尬语定义 | 三类：中二/尴尬抒情、尬夸/捧杀、引战/阴阳怪气（不含"无关自我表演"） |
| 尬语检测方式 | LLM 直接判定（DeepSeek），分批 + JSON 输出 |
| 尬语发送者 | 进入深度画像（与刷屏者同等优先级） |
| AI 画像 | 分层：批量粗筛（全员）+ 重点深掘（单人单调用，带证据包） |
| 深度分析人数 | 阈值制 + 安全上限：所有中/高刷屏风险 + 尬语命中者全进，不设固定 100 人；超安全上限（默认 300）按兴趣分截断 |

## 详细设计

### 1. 流程重排：刷屏检测提前，按兴趣分驱动

现状：Phase 4 按裸弹幕数取 top 100 解析 UID，刷屏检测在 Phase 4.5（解析之后）。

改为：

- 刷屏检测（`spam_detector.batch_detect_spam`，纯本地计算）提前到弹幕采集后
  立即执行，对全部发送者打分；
- Phase 4 的解析名单按**兴趣分**选取（见第 3 节），不再按裸弹幕数；
- 原 Phase 4.5 取消（结果在重排后的位置产出，后续阶段照常消费
  `spam_level`/`spam_score`）。

### 2. 尬语检测（新模块 `src/cringe_detector.py`）

- 输入：合并去重后的全部弹幕（实时池+历史快照合并结果）。按内容去重，
  附出现次数，降低 token 消耗；
- 分批喂给 LLM（约 200 条/批），要求 JSON 数组输出，每条：
  `{是否尬语, 类别(中二抒情|尬夸捧杀|引战阴阳), 理由, 严重度(1-3)}`；
- 按发送者（mid_hash）聚合：尬语条数、类别分布、最高严重度、代表性原文；
- 未配置 LLM_API_KEY 或全部批次失败：整个阶段跳过并打印警告，尬语命中集为空；
- LLM 输出解析失败的批次跳过（降级不中断），解析为空时打印原始响应前 200 字符
  （沿用 `llm_analyzer` 的诊断惯例）。

### 3. 兴趣分与动态定员

- 每个发送者计算兴趣指标：`spam_score`（刷屏检测）、`cringe`（尬语条数与最高
  严重度）、`danmaku_count`；
- **深度名单 = 阈值命中者**：spam_level ∈ {高, 中} 或 尬语条数 ≥ 1 的发送者
  全部进入，不设固定人数目标（普通视频几十人，异常视频自动扩容）；
- **安全上限**：仅当名单总数超过 `MAX_ANALYZE_USERS_HARD_CAP`（默认 300，
  config 可调）时，按 (spam_score, 尬语最高严重度, danmaku_count) 降序截断；
- `--max-users` CLI 参数保留，作为手动硬上限覆盖（传入时优先于阈值制）；
- Phase 5 采集人数跟随 Phase 4 解析结果，不再单独设限（现有 dedup 逻辑保留）。

### 4. 评论贯通展示

- Phase 3 采集的评论已含 uid；建立 uid → 该用户在本视频的评论列表
  （内容、点赞数、时间）；
- Phase 6 画像分析时注入 profile（`profile["comments"]`，上限 10 条，
  按点赞降序）；
- 报告每个用户板块新增"TA 在本视频的评论"小节；
- 该数据同时进入重点深掘的证据包（第 5 节）。

### 5. AI 画像分层重设计（`src/llm_analyzer.py` 重构）

**第一层·批量粗筛**（覆盖全部已采集用户）：

- 沿用分批调用（10 人/批），输出简化为：每人 3-5 个标签 + 一句话定性；
- 成本与现状基本持平。

**第二层·重点深掘**（兴趣分 top K，K = `LLM_DEEP_TOP_K`，默认 20）：

- 每人单独一次调用，输入证据包：
  - 该发送者的全部弹幕原文（刷屏用户截断到前 50 条防超长）；
  - 其在本视频的评论（第 4 节）；
  - 尬语判定结果（类别、理由、严重度、原文）；
  - 刷屏分析（等级、评分、判定理由）；
  - 四维度采集数据摘要（沿用现有 `_build_prompt` 的字段）；
- 输出结构化深评：行为定性 / 动机分析 / 证据引用（原文）/ 风险等级，
  不再限 200 字；
- 单用户失败仅跳过该用户并打印警告（降级不中断）；
- 结果存 `profile["ai_deep"]`，粗筛结果存 `profile["ai_brief"]`。

### 6. 报告改进（`src/report.py`）

- 用户板块"最近投稿"的每个视频标题包
  `<a href="https://www.bilibili.com/video/{bvid}" target="_blank" rel="noopener">`；
- 新增"TA 在本视频的评论"小节（第 4 节）；
- 重点人员展示完整深评（含证据引用），其余展示粗筛标签与一句话定性；
- 报告头部新增"尬语榜"板块：按发送者聚合的尬语条数/类别/代表原文。

### 7. 配置项（`src/config.py` + `config.example.py` 同步）

- `MAX_ANALYZE_USERS`：废止（原固定 100 人上限），由下面的安全上限取代，
  实现时同步清理其在 `main.py` 等处的引用；
- `MAX_ANALYZE_USERS_HARD_CAP = 300`：动态定员安全上限；
- `LLM_DEEP_TOP_K = 20`：重点深掘人数；
- `CRINGE_BATCH_SIZE = 200`：尬语检测每批弹幕条数；
- `--max-users` CLI：手动硬上限（覆盖阈值制）。

### 8. 数据流（重排后）

```
Phase 1  登录
Phase 2  弹幕采集（实时池+历史快照合并去重）
Phase 2.5 刷屏检测（本地，全体发送者）
Phase 2.6 尬语检测（LLM，可降级跳过）
Phase 3  评论 + 充电名单（uid→评论 留存供展示与证据包）
Phase 4  兴趣分驱动解析（批量预验证 MITM，动态定员）
Phase 5  深度采集（跟随解析名单，去重）
Phase 6  规则画像（注入评论）
Phase 7a LLM 批量粗筛（全员）
Phase 7b LLM 重点深掘（top K，单人单调用）
Phase 8  报告（尬语榜、评论小节、投稿超链接、分层 AI 展示）+ CSV/JSON 导出
```

### 9. 错误处理与降级

- 尬语 LLM 全部失败 → 跳过，尬语命中集为空，流程继续；
- 深掘单用户失败 → 跳过该用户，粗筛结果仍在；
- 评论采集失败 → 评论小节与证据包中评论为空（沿用现有降级）；
- 风控：沿用 `-412` / `-352/-403` 重签无效全局冷却（本次已修复的机制）。

### 10. 验证方式（项目无单测框架）

- 聚焦验证：合成 sender_groups 走尬语聚合与兴趣分排序逻辑；
- 端到端：`python run.py BV13MrQBPEec`（已知 7346 条弹幕、5809 发送者、
  高/中风险 16 人的稳定样本），检查：
  - 深度名单包含全部高/中风险与尬语命中者（不受 100 限制）；
  - 报告含尬语榜、评论小节、投稿超链接（可点击新标签页）；
  - 重点人员有结构化深评，其余有粗筛标签；
- `quick_test.py` 同步改为兴趣分选人一样跑通。

### 11. 明确不做（YAGNI）

- 不改动弹幕采集方式（公开接口极限已达）；
- 不做"无关自我表演"类尬语（用户未选）；
- 不做尬语的规则初筛（用户选择 LLM 直接判定）；
- 不引入异步/并发 LLM 调用（限速与简单性优先）。
